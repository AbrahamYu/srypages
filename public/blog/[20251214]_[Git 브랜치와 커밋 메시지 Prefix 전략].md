# Git 브랜치와 커밋 메시지 Prefix 전략

개발 협업 환경에서 Git은 이제 필수적인 도구가 되었습니다. 여러 개발자가 하나의 저장소를 공유하며 작업할 때, 일관된 규칙을 통해 코드 변경 내역을 관리하는 것은 매우 중요합니다. 이때 `Prefix`(접두사)를 활용하면 브랜치와 커밋 히스토리를 훨씬 더 깔끔하고 체계적으로 관리할 수 있습니다.

이 글에서는 Git 브랜치와 커밋 메시지에 Prefix를 어떻게 사용하고, 어떤 상황에서 유용한지에 대해 알아보겠습니다.

## 1. 왜 Prefix를 사용해야 할까?

Prefix를 사용하는 이유는 명확합니다.

-   **가독성 향상**: 브랜치 이름이나 커밋 메시지만 보고도 어떤 종류의 작업인지 빠르게 파악할 수 있습니다.
-   **체계적인 히스토리 관리**: 관련 커밋을 그룹화하고, 특정 기능 개발이나 버그 수정 과정을 추적하기 용이합니다.
-   **자동화의 기반**: Prefix는 Changelog 자동 생성, 버전 관리, CI/CD 파이프라인 연동 등 자동화 도구의 트리거로 활용될 수 있습니다.
-   **협업 효율 증대**: 팀 전체가 통일된 규칙을 따름으로써 코드 리뷰와 의사소통 비용을 줄일 수 있습니다.

## 2. 브랜치 Prefix 전략

브랜치에 Prefix를 사용하면, 현재 진행 중인 작업의 성격을 명확히 나타낼 수 있습니다. 일반적으로 다음과 같은 구조를 따릅니다.

`prefix/기능-설명`

예를 들어, 사용자 로그인 기능을 개발한다면 `feat/user-login`과 같이 브랜치 이름을 지을 수 있습니다.

### 자주 사용하는 브랜치 Prefix

| Prefix     | 설명                                       | 예시                          |
| :--------- | :----------------------------------------- | :---------------------------- |
| **feat/**  | 새로운 기능 추가 (Feature)                 | `feat/add-login-page`         |
| **fix/**   | 버그 수정 (Bug Fix)                        | `fix/login-validation-error`  |
| **docs/**  | 문서 수정 (Documentation)                  | `docs/update-readme`          |
| **style/** | 코드 스타일 변경 (들여쓰기, 세미콜론 등)   | `style/reformat-code`         |
| **refactor/**| 코드 리팩토링 (기능 변경 없는 코드 개선)   | `refactor/simplify-auth-logic`|
| **test/**  | 테스트 코드 추가 또는 수정                 | `test/add-user-api-tests`     |
| **chore/** | 빌드, 설정 등 기타 잡다한 작업 (Chore)     | `chore/update-dependencies`   |
| **hotfix/**| 긴급하게 배포된 버전의 버그 수정           | `hotfix/critical-security-patch`|

## 3. 커밋 메시지 Prefix 전략 (Conventional Commits)

커밋 메시지는 단순히 변경 사항을 기록하는 것을 넘어, 팀의 중요한 자산이 됩니다. `Conventional Commits`는 커밋 메시지에 구조적인 규칙을 부여하는 널리 사용되는 방법론입니다.

커밋 메시지는 다음과 같은 구조를 가집니다.

```
<type>(<scope>): <subject>

<body>

<footer>
```

여기서 가장 중요한 부분이 바로 Prefix 역할을 하는 `<type>`입니다.

### 자주 사용하는 커밋 메시지 Prefix (Type)

| Type       | 설명                                       |
| :--------- | :----------------------------------------- |
| **feat**   | 새로운 기능 추가                           |
| **fix**    | 버그 수정                                  |
| **docs**   | 문서 수정                                  |
| **style**  | 코드 스타일 변경 (포맷팅, 세미콜론 누락 등) |
| **refactor**| 리팩토링 (기능 변경 없는 코드 구조 개선)   |
| **test**   | 테스트 관련 코드 추가/수정                 |
| **chore**  | 빌드, 패키지 매니저 설정 등 기타 변경      |
| **perf**   | 성능 개선                                  |
| **ci**     | CI/CD 관련 설정 변경                       |
| **build**  | 빌드 시스템 또는 외부 종속성 변경          |

### 커밋 메시지 예시

-  **새로운 기능 추가**
    ```
    feat: 사용자를 위한 프로필 수정 기능 추가

    - 사용자는 자신의 이름과 이메일을 변경할 수 있습니다.
    - 프로필 페이지에 '수정' 버튼을 추가했습니다.
    ```

-  **버그 수정**
    ```
    fix: 로그인 시 간헐적으로 발생하던 500 에러 해결

    - 원인: 데이터베이스 커넥션 풀이 고갈되는 문제.
    - 해결: 커넥션 타임아웃 설정을 조정하고, 사용 후 커넥션을 즉시 반환하도록 수정.

    Closes: #123
    ```

-  **리팩토링**
    ```
    refactor(auth): 중복된 인증 로직을 AuthService로 통합

    기존에 여러 컨트롤러에 흩어져 있던 JWT 토큰 검증 로직을
    AuthService의 `verifyToken` 메소드로 통합하여 중복을 제거하고 유지보수성을 높임.
    ```

## 결론

Git Prefix는 단순한 규칙을 넘어, 협업의 효율성을 극대화하고 프로젝트의 품질을 높이는 강력한 도구입니다. 처음에는 다소 번거롭게 느껴질 수 있지만, 팀 전체가 일관된 Prefix 전략을 도입하고 습관화한다면 장기적으로 더 큰 이점을 얻을 수 있습니다.
